# Stage 8: UI

> A small React chat app that streams the agent's progress and answer, shows citations as clickable
> chips, opens the cited note with the passage highlighted, and shows route, cost, and latency per answer.

![answer with citations](../images/ui-answer.png)

## 1. What this stage does

```
browser (React, web/)  ── POST /api/ask {question} ──►  Express (src/server/app.ts)
                       ◄── text/event-stream ─────────   runAgent(..., onEvent)
   event: route       → "Routed to claude-haiku-5-5 (easy: single-fact lookup)"
   event: tool_start  → "search("on-call handoff")"
   event: text        → answer tokens as they arrive
   event: verify      → "Citations verified"
   event: done        → final answer, citations, cost, latency, trace id
click a [1] chip   ── GET /api/notes?path=docs/oncall-policy.md ──► note shown in a side drawer
```

## 2. Concepts

**Server-Sent Events (SSE).** A normal HTTP response that stays open and sends `event:`/`data:` lines
as things happen. One direction (server → browser) is all a chat answer needs.
*Analogy:* a radio broadcast vs a phone call (WebSockets). The browser's `EventSource` only supports
GET, so `web/src/api.ts` reads the POST response stream itself.

**Progressive disclosure of agent work.** Showing "search(...)", "Citations verified" while the agent
works makes a 5-second answer feel responsive and makes the system's behaviour inspectable.

**Rendering untrusted text safely.** Answers and notes are untrusted (they can contain injected text).
`Markdown.tsx` builds React elements and never uses `dangerouslySetInnerHTML`, so no HTML or script in
a note can run in the page.

**Same-origin serving.** In production, Express serves the built UI and the API from one origin: no
CORS configuration and one thing to deploy.

**Basic auth.** Your notes are private; the API has no user system. `BASIC_AUTH=user:password` makes
the browser ask for a login on every request. Always pair it with HTTPS.

## 3. Code walkthrough (read in this order)

1. `src/server/app.ts`: `createApp()`: `/api/health`, `/api/ask` (SSE), `/api/notes` (only indexed
   paths, never outside `NOTES_DIR`), `/api/traces/:id`, static `web/dist`, `requireBasicAuth()`.
2. `src/server/index.ts`: runs migrations, starts the server.
3. `web/src/api.ts`: `ask()` (POST + SSE parsing), `fetchNote()`, `fetchHealth()`.
4. `web/src/App.tsx`: one `Turn` per question; the event handler turns agent events into progress lines;
   `Answer` renders the final answer, drafts, sources, and the cost/latency footer.
5. `web/src/Markdown.tsx`: the tiny safe renderer with `[S#]` citation chips (unknown ids render red).
6. `web/src/styles.css`: Notion-like look, dark mode via `prefers-color-scheme`, mobile drawer.
7. `tests/stage8-server.test.ts`: SSE stream, validation, path traversal, basic auth.

## 4. Decisions

- SSE over WebSockets (D-025).
- One Node process serves API + UI; optional basic auth (D-026).
- Deploy target: one container + managed Postgres with pgvector; steps in the README (D-027).
  The Dockerfile and compose file were written but **not built in the build sandbox** (no Docker daemon).

## 5. Run it

```bash
# terminal 1: API (reads .env)
npm run server
# terminal 2: UI with hot reload on http://localhost:5173 (proxies /api to :8787)
npm --prefix web install && npm run web:dev
# or production-style, one process on http://localhost:8787:
npm run build && npm start
```

## 7. Interview questions

1. **SSE or WebSockets for streaming LLM output?** SSE: one-way, plain HTTP, works through proxies,
   auto-reconnect; WebSockets when you need two-way, low-latency messages (e.g. interrupting
   mid-stream from the client over the same channel).
2. **How do you render model output safely in a web UI?** Treat it as untrusted: escape by default,
   use a renderer without raw HTML, sanitise links, and never execute generated code in the page.
3. **What would you show users about how an answer was produced?** Sources with the exact passage,
   the steps the agent took, refusals with a reason; optionally cost/latency for internal tools.
4. **How do you handle a user closing the tab mid-answer?** Detect the closed connection, stop sending,
   and ideally abort the model call (pass an `AbortSignal`) to stop paying for unused tokens.
5. **How would you add authentication for a multi-user version?** An identity provider (OAuth/OIDC),
   per-user note collections with row-level filtering in retrieval, and per-user traces and budgets.
